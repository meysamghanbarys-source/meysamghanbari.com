# Satellite Applications Atlas

The Atlas is a static Astro destination at `/satellite-applications/`. Technology in the desktop and mobile navigation, the homepage technology section and the footer provide entry points. Only published records are built. The homepage stays independent of the number of applications.

## Content and navigation

Store one approved civilian application per JSON file in `src/data/atlas/articles/`. Start from the oil-spill record for the field names. Each file represents a complete publication. Preserve its ID, primary industry and slug on subsequent reviews. Store public images and their responsive sizes in `public/images/atlas/`. Each image includes its scene description, alternative text, rights link, source, credit and dimensions. The two required assets are the hero and an observation or mission example. A third hardware photograph is optional. The mission evidence, costs, workflow, orbit comparisons and geographic markers render from structured text and values.

Definitions for the nine industries, routes, family anchors and orbit guide are in `src/data/atlas/taxonomy.ts`. One canonical URL serves each application. Related guides use shared industries, families and technologies. An industry with its first published article automatically gets its own route. Other industries supply expandable topic summaries and a truthful zero count. The public directory renders 12 cards per page. A small search index is requested only when a filter or query needs it. Ordinary pagination, category links and all article content are available without JavaScript. Static sitemap and image-sitemap entries are generated by the existing build.

The current Atlas hero is a neutral map illustration. To fit a supplied landing photograph, update the scoped hero artwork and its gradients in `src/styles/atlas.css`. Supply optimized mobile and desktop crops and check legibility at the six release widths. Keep observation assets distinct from conceptual illustrations. The globe and the equirectangular market basemap use Natural Earth public-domain 1:110m land polygons. Numbered map markers correspond to the adjacent written market examples.

## Daily operation

The Work task **Publish Satellite Applications Atlas** is the one production scheduler. Its clock is 08:00 Asia/Qatar every day. It uses the connected GitHub account, web research, image sources and the owner's private editorial queue. No local machine, paid generation API, extra account or cron service is part of this design. Trigger time and public availability are separate events.

The private queue is named **Satellite-Atlas-Editorial-Queue.json**. The scheduled task contains its file identity. The file records stable topic IDs, priorities, scope, buyers, geographic and technical context, progress and release outcomes. Keep drafts, unpublished research and run failures in the private workspace. Merge duplicate proposals into their canonical topic. Mark a selected candidate `research`, record its sources and rights, advance through `verified` and `ready`, and mark `published` after the host serves the correct page. When the queue runs low, research fresh civilian candidates before replenishing it.

1. Reconcile the Doha calendar date and topic against main, the public host and the private log. Resume pending deployment if source already contains the day's article. When the page is already live, reconcile its log and return its verified URL. Keep one article per actual release date.
2. Check primary engineering sources, mission status, commercial examples and image licences. Explain how the company will use the result. Compare existing service, hosted payload and dedicated spacecraft. Include the price year, currency, units and installation/operating exclusions. Record the basis for estimates and quotation-only items. Check external references by opening them, especially PDFs and changed vendor URLs.
3. Build from a fresh checkout of the current main or a release branch. Use `npm ci`, `npm run build`, `python scripts/check-built-site.py` and `python scripts/check-publication-library.py`. The build first runs `scripts/check-atlas.mjs`. It checks civilian scope, duplicate IDs, topics and publication dates, links between claims and sources, comparison fields, image credits and file paths. Human review of evidence and rights remains essential.
4. Preview the built pages at 320, 390, 768, 1024, 1440 and 1920 CSS pixels. Check search, zero results and reset, menu disclosure, the industry path and family anchor, the cost panel, image credits, contact navigation, keyboard focus and no-script reading. Check at least a phone and desktop before releasing new images and unusually long headings.
5. Commit the reviewed article and its assets together. Confirm the current head before advancing production. Use a fast-forward push or merge through repository rules. If another edit arrived, rebase the change, recheck the date and topic, rebuild and rerun checks. Cloudflare Pages builds the main branch with `npm run build` and publishes `dist/`.
6. Inspect the actual page content on meysamghanbari.com, its image variants, industry, catalogue, sitemap and contact route. Write the evidence to the private log, including the date, article ID, canonical URL, commit, source links and deployment outcome. Replace the private file with its expected version. On a version conflict, reconcile the two records against current public state before writing again.

## Failure handling and manual control

Retry a transient source or deployment status check with bounded backoff. Use a confirmed replacement when a source or image licence becomes unavailable. If a material gate still fails, retain the draft privately, log the problem and alert the owner. A public route missing after a commit is a pending or failed deployment. Check the provider status for the matching commit before retrying and never submit a second article for that date. A missed morning is recorded as a gap. The next run publishes at most one article with its actual date. Add an entry to the log even when no article is released.

A manual run uses the same Work task and the same duplicate check. Pause or resume that task to control future runs. To withdraw a defective release, revert only its commit with a new change on the latest branch, run the checks again and verify the production URLs. Record the rollback in the private log. Correct an existing article by keeping its canonical URL and publication date and advancing the review date after rechecking affected sources.
